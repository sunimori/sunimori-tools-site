1Check of web.xml deployment settings (development stage, directory listing, session, etc.)SR-CFG-WEBXML-001WarningSecurity

Reports 6 kinds of settings explicitly written in WEB-INF/web.xml that weaken protection or leak debugging information when deployed to production. (1) The JSF project stage is Development. (2) STATE_SAVING_METHOD is client and there is a setting that can disable view state encryption (such as com.sun.faces.disableClientStateEncryption). (3) Directory listing is allowed on the default servlet of Tomcat/Jetty (listings, dirAllowed). (4) session-timeout is 0 or less (the session never expires). (5) session-timeout is longer than 1440 minutes (can be changed with a parameter). (6) The session cookie has http-only=false. The following are not reported: a missing session-timeout, a setting of only STATE_SAVING_METHOD=client (it is encrypted by default), a stage other than Development, and placeholder values that are replaced at build time. Because it is not known whether web.xml is deployed to production, this finding is a prompt to check.

         xsi:schemaLocation="http://xmlns.jcp.org/xml/ns/javaee http://xmlns.jcp.org/xml/ns/javaee/web-app_3_1.xsd"

  <display-name>demo</display-name>

Finding message (the engine's actual output)

Check this web.xml deployment setting: javax.faces.PROJECT_STAGE = Development in context-param.

Fix (the engine's suggestion)

First check whether this web.xml is deployed to production (development and production descriptors are often switched by the build). If it is, act on the sentence below that matches the setting name of this finding (javax.faces.PROJECT_STAGE): [JSF project stage] use the Production project stage, or remove the setting (Production is the default). [View state encryption] remove the parameter (Mojarra's com.sun.faces.disableClientStateEncryption whatever its value; MyFaces' encryption parameter: remove it or set it to true); client state is encrypted by default, and if a fixed key is needed, configure the key instead of switching the encryption off. [Directory listing] set listings (Tomcat) or dirAllowed (Jetty) to false; the default is false for Tomcat and true for Jetty, so for Jetty false must be written. [Session never expires] give session-timeout a finite, reasonable number of minutes. [Session timeout too long] shorten session-timeout to a reasonable number of minutes (the unit is minutes, not seconds). [Session cookie] remove http-only=false. If the setting is intended, suppress it in suppressions.yaml with the reason.

Note on the NG example: If the project stage is left as Development when deployed to production, debugging information (such as error messages) is shown to users. Because it is not known whether this web.xml is for production, this finding is a prompt to check.

3Variable referenced more than once in an array initializerSR-JAVA-ARRAY-001WarningGeneral

Reports when the same variable (the same declaration; for an instance field, one whose receiver can be proven to be the same) is read more than once among the direct elements of the same array initializer. The length of an array (names.length) is not a variable read, so it is not compared, and no limit is reported when type bindings are enabled. If another direct element of the same initializer increments or assigns the variable (n, n++, n++, n), the initializer as a whole is not compared. When a name cannot be resolved, it is not compared as text; only when the same text appears twice and no decision can be made is it reported as a "part that could not be determined", and nothing is output for names that differ from each other (Keys.NAME, Keys.AGE). Some input may have been left out after copy and paste, but the duplicate may also be intentional. It does not depend on business-related names.

Detection scope

Code forms detected

  • Among the direct elements of an array initializer {…}, the same variable is read twice or more: new Object[] {a, b, a} (cases P01, P02, B02). The declaration form Integer[] r = {a, b, a}; counts as well (P05). The element type does not matter; int[] is examined too (P17).
  • Not only method bodies: array initializers in constructors (P06), instance initializer blocks (P07), static initializer blocks (P08), field initializers (P09), lambda bodies (P10) and methods of anonymous classes (P11) are examined, and so is one that is an argument of a call, use(new Object[] {a, b, a}) (P12).
  • Three kinds of variable are compared: local variables and method parameters (P01, P02, P13); instance fields (value, this.value, Outer.this.value and super.value count as one variable when they name the same field; P03, F06B, P14, P15, P15B); fields of the same local variable or parameter, such as left.value (P04, P16).
  • Redundant parentheses around an element are removed first: (a) equals a (P02).
  • A repeated variable gives one finding, located at its second occurrence, with the other occurrences as related locations (B02: three occurrences, still one finding). Two different repeated variables in one array give two findings (B07), in the order of the variables' first occurrence (B09; the table of the HTML report is sorted by line instead). The name shown is the one written at the first occurrence: with value and this.value mixed it is value (F06B).

Conditions

  • The initializer has at least 3 direct elements (parameter minElements, default 3). A literal counts as an element ({a, a, 0} is examined; B11), a trailing comma does not ({a, a, } has 2; B12); smaller initializers are not examined (B04).
  • It must be the same declaration, and the declaration must be resolvable. The same name with a different declaration does not count: a local value and the field this.value (F06), or the field x of an inner class and Outer.this.x (N15). A variable whose declaration cannot be resolved is not compared (see "When it cannot judge").
  • A field read needs a receiver that is proven to be the same object. Proven receivers: this, no receiver, Outer.this, super, and a local variable or parameter that is not reassigned inside that initializer (P03, F06B, P14, P15, P04, P16, N11). Other receivers: see "Not detected".
  • The rule applies to **/*.java (test sources included) and not to files below any directory named generated or target, at any depth; matching is case-sensitive, so Generated or generatedx are not excluded (scope.include, scope.exclude).
  • In a review of changed code only (scope.changedCodePolicy: INTERSECT_CONTAINER): when any line of an initializer was changed, the repetitions in the whole initializer are reported, including one that existed before the change and whose two reported places are both unchanged. Repetitions in an initializer without a changed line are not reported, but what could not be judged there is still recorded.
  • This statement describes the package defaults. A project may change parameters in ruleOverrides; the report's "Review conditions" then records that this rule's parameters were changed (the fact, not the values): ignoreLiterals (default true; false also compares identical literals; pm01), ignoreCompileTimeConstants (default true; pm02), referenceKinds (default local variable, parameter, instance field; STATIC_FIELD can be added; pm03), minElements (default 3, 2 to 100000; pm04), minIdentityQuality (default RESOLVED, can be lowered to RECOVERED or SYNTAX_ONLY; pm05).
  • Which review profiles (--profile) enable this rule by default is generated by smartreviewer rules doc from the actual profile definitions: it is the row "default enablement by profile" of this rule in the rule overview (which is written in Chinese).

Not detected

  • Literals and null (N02, N03), and compile-time constants: static final constants (N04), and final locals and final fields initialized with a constant expression (N13).
  • Elements that are not a direct read of a variable: method calls (N05), casts and operator expressions (N10), increments such as a++ (F07), and array element reads (row[0]), conditional expressions, new, this, class literals, lambdas, instanceof, negation and string concatenation (B21). A variable read directly next to them is still compared: {a, c ? a : b, a} reports a (B21).
  • The length of an array (names.length) is not a variable read: it is not compared and causes no limitation (fx01, fx02). That holds when type bindings are on; with type bindings off see "When it cannot judge".
  • When another direct element of the same initializer is itself an increment, decrement or assignment of the variable (n++, ++n, n = m, n += 2), the variable is left out as a whole, reads before the change included, even when two reads still have the same value ({n, n, n++}): {n, n++, n++, n} (fx03, N14). A change hidden elsewhere is not recognised (see "Known false positives and negatives").
  • Static fields are not compared, whether final or not, including Cls.counter, enum constants and the spelling through an instance: the default kinds of variable do not include static fields (parameter referenceKinds; N08, N16).
  • Fields with different receivers, such as left.value and right.value (N06). When the receiver is none of the kinds that "Conditions" lists as provable, the field read is not compared either, for example an array element (hs[0].value), a field chain (p.inner.value, this.h.value), a field used as receiver, the result of a method call, a cast, or a variable that is reassigned inside the initializer (N06B, N11, N17, N17B, N17C, N17D, N17E, N18).
  • Nested initializers are not flattened: the outer array and each inner array are examined on their own, and the elements of an inner array are not mixed into the outer comparison (B03, B08).
  • Each initializer is judged on its own: the same variable in another array (in the same method or in another method), or its value kept in another variable (copy = a), is no repetition (N12).

When it cannot decide

  • A name that cannot be resolved (undeclared, or type information missing) is not compared as text. Only when the same text stands twice in one initializer is the coverage limitation IDENTITY_UNAVAILABLE reported, and that review result is incomplete; different unresolved names cause no limitation (B05, fx05, fx04).
  • When the base class cannot be resolved, two spellings of the same field are two different texts: {inherited, o, this.inherited} is neither compared nor reported as a limitation, so the repetition is not found and the file still counts as completely checked (B13).
  • With type bindings off (resolveBindings: false), local variables, parameters and instance fields declared in the file (names.length too) have only a syntax-level identity, below the RESOLVED the rule requires: in an array of 3 or more elements every such read, repeated or not, reports IDENTITY_QUALITY_INSUFFICIENT, nothing is compared and the result is incomplete (B05S, B14, B25A). Not reported: static fields by simple name, final variables initialized with a literal, variables another element changes (B25); a final local initialized with 2 + 3 is reported (B25B).
  • Without type bindings these names are unknown too: one the file does not declare (an inherited field inh read by its simple name), super.sx, a static field or constant qualified by its class (Cls.sf, Cls.SC), an enum constant Color.RED, a field chain h.value. IDENTITY_UNAVAILABLE is reported only when the same text stands twice in an initializer, and the review result is then incomplete (B25C, B25D, B25E, B25F, B25G, B25H); one read of each records nothing (B25I).
  • It also happens with type bindings on, when the lambda itself cannot be typed: it is passed to a method of an unknown type (svc.each(x -> {…})) or to one whose type arguments are unknown (list.forEach(y -> {…}) over a List<Unknown>); a written parameter type, (Integer x) -> {…}, does not help. The local variables and parameters read inside it (even once) have only a syntax-level identity and IDENTITY_QUALITY_INSUFFICIENT is reported; a repeated variable gives no finding (B15, B15B, B15C, B15E, B15F, B15G).
  • A lambda assigned to a declared type is typed even when a type argument of that type is unknown, so nothing is limited there: in Function<Unknown, Object[]> g = u -> {…} a repeated u is reported (B15D).
  • A damaged array gets CONTAINER_MALFORMED from the rule only if the parser marked the initializer as recovered and at least minElements elements are left ({a, b, a,, }); it is then not examined (B06). Other damage — a missing comma ({a b a}), a missing closing brace ({a, b, a;), fewer than 3 elements left ({a, a,, }) — can leave it unexamined and the rule reports nothing (B17, B18, B19). But a file with syntax errors is itself recorded as PARSE_RECOVERED (not judged, one per error): the result is incomplete and --strict-coverage exits with 3 for all four (B06, B17, B18, B19).
  • When a single element is damaged ({a, b +, a}), ELEMENT_MALFORMED is reported and the review result is incomplete; the other elements are still compared and a repetition is still reported, and the file is recorded as PARSE_RECOVERED as well (B20).
  • With type bindings on, a field read whose receiver cannot be proven the same is recorded as RECEIVER_UNPROVEN for every such read (even a single one) and left out of the comparison. It does not make the review result incomplete, but the report counts it among the "Parts not judged" (N06B, N11, N17, N17B, N17C, N17D, N17E, N18).
  • Arrays in annotation values: by default they give no finding (the elements are constants; N19). In annotations of methods, constructors, parameters, local variables, enum constants, interface methods, annotation type members and their defaults a repeated undeclared name is reported as IDENTITY_UNAVAILABLE (B16, B16C, B16P, B16L, B16E, B16I, B16M, B16D); arrays in annotations of classes, fields and record components are not examined (B16K, B16F, B16R).

Known false positives and false negatives

  • False positive: an intentional repetition, for example x standing for both the start and the end of a range, {x, y, x}. The tool cannot judge the business meaning, so a finding only asks for a check (confidence MEDIUM). When the repetition is confirmed as intended, an inline suppression can be used (next item); the original finding is still counted as suppressed (N07).
  • An inline suppression covers a finding when its target line is the line of the finding's location (the second occurrence: disable-next-line above that line, su05; disable-line at its end, su06; the other findings of the initializer stay, su07) or the line where the { of the initializer stands (then every finding of the initializer: su01, su08, su12, su13). One above the first occurrence, or above a statement whose { stands alone on the next line, does not apply and the findings still appear (su02, su11). For the general rule see "Suppression" in the README.
  • The reason is required: a marker without one, or with an empty one, covers nothing and the finding appears (su09, su10). The expiry until may be omitted when no team policy applies, and a marker whose date has passed no longer applies (su04, su03). When the rule package's teamPolicy.maxSuppressionDays is in force (the policy needs protectedRules or minimumSeverity as well), a marker without until, or with an until further away than that many days, is not permitted (suppression.status is NOT_PERMITTED in the JSON) and the finding appears.
  • False positive: the value of a variable changes between two reads and the rule does not see it. The change comes from a method call ({count, next(), count}, where next() changes count; B22), or an increment or assignment is hidden inside a call, an index, a conditional expression, an operation or parentheses ({n, id(n++), n}, {n, (n++), n}; B23).
  • False positive: a local that is never changed but is not final is no constant: {k, k, k} after int k = 3; is reported (B24).
  • False positive relative to a baseline: the fingerprint of a finding contains the number of the array initializer among those of its method (evidence containerId, such as …#m(Integer,Integer)/array[1]). Inserting another array initializer before it in the same method changes that number and the fingerprints of the findings after it: old findings recorded in a baseline reappear as new ones, and suppressions written by fingerprint no longer apply (B10A, B10B).
  • False negative: the same variable among the arguments of a method call (Arrays.asList(a, b, a), List.of(a, b, a), varargs), or an array filled element by element (r[0] = a; r[2] = a;) is not examined, because the rule examines array initializers only (N09).
  • False negative: initializers with fewer than 3 elements ({a, a}) and static fields are not examined by default. That does not mean there is no risk (B04, N08).
  • False negative: a repeated value that comes from a method call ({load(), load(), x}), passes through a cast or an operator, or is kept in another variable (copy = a, {a, copy, d}) is not recognised, because the rule does not follow values (N05, N10, N12).

6Assignment in a condition (== written as =)SR-JAVA-ASSIGN-CONDITION-001WarningGeneral

Reports when the condition itself of an if, while, do, for or conditional operator is an assignment (if (flag = true)). The value of the condition is the assigned value, and the variable is also overwritten. Usually == was intended. It is reported when the assigned value is a literal or a variable. Assigning the result of a method call or the like (if (found = find(key))) may be intentional, so it is not reported by default (parameter values), and saving a variable of the same name in a field and testing it (if (this.skip = skip)) is not reported either.

NG example (code that is reported)

String label(boolean member) {
    if (member = true) {
        return "member";
    }
    return "guest";
}

Finding message (the engine's actual output)

boolean configure(boolean skip) {
    if (this.skip = skip) {
        return false;
    }
    return true;
}

Saving an argument of the same name in a field and testing that value is intentional, so it is not reported.

7Self-invocation of a Spring async methodSR-JAVA-ASYNC-SELF-001WarningGeneral

Reports a call to a method that has @Async, either on the method or on its class, when it is called directly with this (including an implicit this) from the same class or a subclass (including inherited async methods). A call that does not go through the Spring proxy does not become asynchronous and is executed synchronously in the calling thread. private, static and final methods, where the proxy cannot intervene, are not reported (the same applies when @Async is on the class). It is not reported when adviceMode is set to ASPECTJ or when the same file has @EnableAsync(mode = ASPECTJ). Calls through another object are not reported either. Requires type information.

NG example (code that is reported)

public void asyncBad() { this.send(); }

Finding message (the engine's actual output)

Spring async self-invocation: send.

Fix (the engine's suggestion)

Move the @Async method to another Spring bean and call it through the injected bean (e.g. asyncService.send()), or use AspectJ mode (@EnableAsync(mode = AdviceMode.ASPECTJ)), which also covers calls inside the class.

OK example (code that is not reported)

It is called through another object (a bean injected as a proxy), so it runs asynchronously.

Example that is not reported (boundary or exclusion)

    flush();
}

The called flush() is a final method; the Spring proxy cannot intervene and @Async has no effect, so this rule does not cover it.

Finding message (the engine's actual output)

68Resource not closed (streams, JDBC, etc.)SR-JAVA-RESOURCE-LEAK-001WarningGeneral

The remaining problem is that the statements and result sets stay open until the caller closes the connection and can accumulate within one request. A statement that is reported again by disabling ignoreOwnerReleased is also handled this way if the connection is a parameter.
